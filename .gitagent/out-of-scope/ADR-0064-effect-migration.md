# ADR-0064: Migrate OpenGantry to Effect (5.0) — Effect Schema replaces zod, core depends on effect, no new network path

**Status: ACTIVE** (issue [#400](https://github.com/jeger-ai/opengantry/issues/400); owner sign-off 2026-11-25, re-decisions the same day, decisions D1 and D2 and the 5.0 decisions R1 to R4 on 2026-11-26; recorded in MSN-0410, slices S1.1 and S1.1a). This record carries the decisions. The plan is spec v5.3 on #400, signed by the owner on 2026-11-26. The work ships as one breaking 5.0 major in six phases, one Tier-3 Planner mission per slice.

## Context

Issue #400 asks to move OpenGantry to [Effect](https://effect.website): typed errors, scoped lifetimes for processes, sockets, temp directories and locks, services with live and test layers, and one schema library. Measured on 2026-11-25 (`scripts/effect-inventory.sh`): 26 sync spawn calls in 16 production files, 8 async spawn calls, 177 `readFileSync`/`writeFileSync` calls in 84 files, 14 zod importers, 16 commander importers, 14 hand-written `Error` classes and 37 `Date.now`/`setTimeout` calls.

`effect` 4.1.5 has no dependencies. Platform, CLI and schema live inside it (`effect/process`, `effect/cli`, `effect/schema`); the v3 packages `@effect/platform` and `@effect/cli` are not used. It also ships network modules (`effect/http`, `effect/net`, `effect/rpc`, …). `@effect/platform-node-shared` 4.1.5 provides the Node layers and depends on `ws` and `@types/ws`; its barrel (`dist/index.js`) re-exports `NodeWS` (`export * from "ws"`), `NodeDns`, `NodeDatagramSocket` and `NodeAddressResolver`, and `NodeSocketServer.js` statically imports `NodeWS.js`. `@effect/platform-node` requires redis as a peer dependency and brings undici.

## Decision

### Owner answers (2026-11-25)

| Point | Decision |
|---|---|
| P1 Ambition | Full migration: every package and the CLI. |
| P2 Schema | Replace zod with Effect Schema. |
| P3 Core | Core depends on `effect` (amends ADR-0054). |
| P4 Surface | Superseded by R1 (2026-11-26). Was: Effect inside the bundles; the public API stays Promise-based or sync (4.x, no break). |
| P5 CLI | `effect/cli` replaces commander. |
| P6 Budgets | Superseded by R4 (2026-11-26). Was: net ≤ 0 production lines per phase; ratchet `ARCH_BASELINE.json` after each phase. |
| P7 JSON Schema | Same verdicts; the generated bytes may change once (CHANGELOG). Canonical JSON, digests and signatures stay byte-identical. |
| P8 Platform | Superseded by P8′. |

### Re-decisions (2026-11-25)

- **P2″** No zod exception. `mcp-tools-register.ts` keeps one Effect Schema per tool, generates its JSON Schema, and registers tools through the MCP SDK's low-level `Server` (`ListTools`/`CallTool` handlers). zod stays only as a transitive dependency of `@modelcontextprotocol/sdk`: no registry row, no importer.
- **P4′** Superseded by R1. Was: `verifyInput` becomes an Effect Schema and is the only allowed change to the public type surface.
- **P6′** Superseded by R4. Was: phases 1 and 2 ship as one release, and net ≤ 0 is judged over their sum.
- **P8′** The live layers come from `@effect/platform-node-shared` only. `@effect/platform-node` is not used.

### Owner decisions (2026-11-26)

- **D1. Network-capable code is unreachable** (this restates G7 of the issue #400 spec, which said "`effect/http` and `effect/net` are unreachable"). The root `effect` module cannot meet the old wording: `effect/dist/Schema.js` (lines 38–64) statically imports nine pure-data modules, `http/Cookies`, `http/Headers`, `http/UrlParams` (with its internal `http/internal/urlParams`), `net/Dns`, `net/Host`, `net/IpInterface`, `net/IpNetwork` and `net/NetAddress`. Nothing in effect's `dist/` imports a Node network built-in. The direct-import ban on Effect's network subpaths stays; S1.1a turns it into an allowlist (see Network). `NodeSocket` leaves the allowlist: `NodeSocket.js` lines 80 and 288 open `Net.createConnection` and `Tls.connect` to any host. The admission broker (S2.6, S2.7) uses raw `node:net` only inside `packages/git/src/platform.ts`, as the one owned exception; `node:net` is not banned yet, because today's users stay until S2.6 moves them.
- **D2. `scripts/arch-net-sum.mjs` is not wired into `scripts/dev-validate.sh` in S1.1.** That file is a copy of `templates/scripts/dev-validate.sh` (`npm run build` copies it back), and `templates/` is outside this slice. The release slice (S6.8 in spec v5.3) wires it, with `templates/` in its mission scope, against the tag `v4.1.0` (R4). Run against `origin/main` in the middle of the release, it would fail by design.

### Owner decisions for 5.0 (2026-11-26)

- **R1 (replaces P4, P4′).** The public APIs are Effect-native in 5.0. There are no Promise bridges. An export that does I/O or can refuse returns `Effect<A, E, R>` with typed refusals that carry `gxtCode`, `message`, `hint` and `exitCode`. A total, pure export stays a plain function. Each package exports one `…Live` layer. `GantryUserError` is removed. Consumers, OpenHangar first, are updated in the same release.
- **R2.** The CLI may break, and every caller is updated in the same release. These invariants stay:
  - I1: `--version` prints the bare semver on the first line, on all three bins.
  - I2: `hook <name> "$@"` passes git's arguments and stdin through.
  - I3: cage exits 3 and 4, and its `cage: <status> — ` stderr line.
  - I4: `--` passes argv through verbatim, the child's exit code comes back, or 128+N on a signal.
  - I5: `GXT_*` codes, the stderr format, the `--json` failure envelope and the MCP error fields.
  - I6: the machine outputs that shipped templates read.
  - I7: P7.
  - I8: the exit classes; argv usage errors may move from 1 to 2.
  - I9: the shim environment variables.
  - I10: MCP tool names and argument names.

  Every changed conformance golden is a row in `test/conformance/CHANGES-5.0.md`.
- **R3.** P7 is unchanged.
- **R4 (replaces P6, P6′).** One 5.0 major. Phase 1 lands on `main` without changing 4.x behaviour. The other phases land on `release/5.0`, which merges into `main` at the release. Net production lines over all layers, measured from `v4.1.0` to the release head, are ≤ 0. At the end of phase 3, a positive running sum stops the work for an owner decision.
- **O1.** At each phase checkpoint the owner publishes `5.0.0-next.N` under the npm tag `next`.

Consequences of R1 to R4 that the spec judges required:
- **The verify bundle inlines the `effect` runtime.** It re-exports `Effect`, `Exit`, `Layer` and `Cause` from its main entry, so OpenHangar's vendored handover gate still runs with only node and git. `effect` is also in verify's `dependencies` at the exact pin, for the published types only.
- **The upgrade from 4.x runs 5.0 through `npx` while 4.x is still installed.** The order is plan, Planner commit, apply, `npm i -g`, then commit. The 4.1.0 hook shims refuse another major, and 5.0 cannot change them.
- **Synchronous 4.x code reaches ported code through our own service tags** (`GitService`, `FsService`, `ProcService`). They have a sync live layer (`PlatformSyncLive`) and an async one (`PlatformLive`, over the six platform modules). `runBridgeSync` and `runBridgePromise` take the layer as an argument. Once no sync bridge is left, the sync layer is deleted.

### Amendments

- **ADR-0052 A6:** "one schema library, zod" becomes "one schema library, Effect Schema", with JSON Schema generated from it. zod is removed from `package.json` and the registry when its last importer goes (phase 2).
- **ADR-0052 B7:** "one schema library" now means Effect Schema; core's runtime dependencies follow ADR-0054 as amended below.
- **ADR-0054 decision 1:** core depends on `effect` and `yaml`, nothing else, and stays I/O-free. Core may import the pure `effect` modules. It may not import `effect/process`, `effect/socket`, `effect/cli`, `effect/FileSystem` or `effect/Path`, nor name `FileSystem`, `Path`, `ChildProcess` or `ChildProcessSpawner` in an import from `"effect"`.

### Network: ADR-0055 upheld

Effect adds no network path. ADR-0052's non-goal and ADR-0055's single opt-in exception (keyless signing through `sigstore`) stand. The existing network paths are unchanged, and they are the **named exceptions**:
- policy pull and deps fetch;
- keyless signing (`sigstore`);
- `missions/src/npm-ci/fetch.ts` (`node:https`, `node:tls`);
- the GitHub host broker `missions/src/admission/github-client.ts` and the architecture fetch `missions/src/arch/external/architecture-fetch.ts` (global `fetch`);
- the sandbox probe `cage/src/sandbox-probe/probe.ts` (`node:net`, `node:dgram`);
- until S2.6, `missions/src/admission/{client,serve}.ts` (`node:net`, the local broker socket); from S2.6, `packages/git/src/platform.ts`.

S3.8 adds the whole-tree `node:` network bans, with these files as owners.

**Allowed subpaths of `@effect/platform-node-shared`:** `NodeFileSystem`, `NodePath`, `NodeChildProcessSpawner`, `NodeRuntime`, `NodeStdio`, `NodeTerminal` (D1). Only `packages/git/src/platform.ts` may import them. None of them imports `ws` or a Node network built-in (checked in the 4.1.5 `dist/`). Through `effect` they may reach the nine pure-data `http` and `net` modules of D1, which open no connection.

**Banned modules**, in every production file:
- `ws`, `undici` and `@effect/platform-node`, each with any subpath;
- the bare `@effect/platform-node-shared` (the barrel) and every subpath outside the allowlist: `NodeSocket`, `NodeWS`, `NodeSocketServer`, `NodeDatagramSocket`, `NodeAddressResolver`, `NodeDns`, `NodeClusterSocket`, `NodeHttpCompression`, `NodeCrypto`, `NodeSink`, `NodeStream` and any later addition;
- every `effect` specifier outside an **allowlist** (S1.1a):
  - `effect`;
  - one-segment root modules (`effect/Schema`, `effect/Clock`, …);
  - `effect/schema`, `effect/cli`, `effect/process` and `effect/encoding`, each with any subpath;
  - `effect/testing`, only in `packages/*/src/testing/`.

  So `effect/socket`, `effect/http`, `effect/net`, `effect/rpc`, `effect/jose`, `effect/reactivity`, `effect/crypto` and the rest are banned, including modules such as `effect/socket/Socket` and `effect/http/FetchHttpClient` that the package's `./*` export reaches.

**Enforcement** in `TARGET_ARCHITECTURE.yaml`, judged over the whole tree by `gantry arch check`:
- `RULE-NET-EFFECT` bans the modules above in static `from`, side-effect `import "…"`, dynamic `import(…)` and `require(…)`, in single, double or backtick quotes;
- `RULE-CORE-EFFECT-PURE` bans Effect's I/O modules in `packages/core/src/**`;
- `OWNER-EFFECT-PLATFORM` makes `packages/git/src/platform.ts` the only importer of `@effect/platform-node-shared`;
- `OWNER-EFFECT-TESTING` keeps `effect/testing` in `packages/*/src/testing/` (tests are outside the scan);
- `OWNER-NET-GLOBALS` allows global `fetch` (bare, through `globalThis`, `global`, `self` or `window`, with `?.` or `["fetch"]`) and `WebSocket` only in the two files that use global `fetch`. These need no import, so the import rules cannot see them, and the main package is not bundled. Spec v5.3 calls this rule `RULE-NET-GLOBALS`; it is an owner rule because its owners are exactly the named exceptions.

The rules are regex pattern and owner rules, because import rules match a specifier substring only. They judge the text of direct imports, with known limits:
- a comment such as `// do not import "ws"` matches (a false positive, the safe direction);
- a comment between keyword and specifier (`import /* c */ "ws"`) gets past;
- a template literal with an interpolation (``import(`ws${x}`)``) gets past; only a plain backtick specifier is caught;
- a member used through a namespace (`E.FileSystem` after `import * as E from "effect"`) is not seen;
- what a module reaches through other modules is not seen; the root barrel `effect` itself reaches `persistence`, `sql`, `reactivity` and `crypto` internally, so the rules judge specifiers and the bundle scan judges what ships;
- a method or function definition named `fetch` matches `OWNER-NET-GLOBALS` (a false positive, the safe direction); name such members otherwise;
- `fetch` used as a value (`{ fetch }`, `const f = fetch`) gets past `OWNER-NET-GLOBALS`;
- `createRequire(import.meta.url)("…")`, or a `require` function under another name, gets past every import rule.

The main package is not bundled (its `exports` point at `dist/cli/*.js`), so for it these rules are the only guard against a direct import. The slim cage and verify bundles also get the esbuild metafile check (S1.2). It bans `ws`, `undici`, `node:http`, `node:https`, `node:http2`, `node:net`, `node:tls`, `node:dgram`, `node:dns` and the banned `Node*` modules when they are reached through Effect. It names the nine data modules of D1 as allowed, and it scans the output for `globalThis.fetch`, `fetch(` and `WebSocket` outside the named exceptions.

### Conventions

- A service is `XService` (the tag), its live layer `XLive`, its test layer `XTest`. Test layers live in `packages/*/src/testing/`.
- Refusals are `Data.TaggedError` families that carry today's `GXT_*` code (`gxtCode`), `hint` and exit code (`exitCode`).
- `Effect.runSync` and `Effect.runPromise` appear only at entries and in `packages/core/src/run-bridge.ts`.
  - It provides `runBridgeSync` and `runBridgePromise`. Both take the layer as an argument and rethrow the original failure.
  - An unported caller reaches ported code through a bridge until it is ported itself.
  - No bridge is left at the release.
- **Lint L1** bans every error-channel combinator that can drop a failure. An allowed use carries `// eslint-disable-next-line no-restricted-syntax -- refusal-ok: <reason>`. Only these files are exempt as a whole: `src/cli/exit.ts`, `packages/core/src/run-bridge.ts` and `packages/git/src/{platform,services,git-service,fs-service,proc-service}.ts`.

### Budgets

Cold start and bundle size budgets: measured in S1.2, signed by the owner before S1.2b.

## Consequences

- Adopters install `effect`, `@effect/platform-node-shared`, `ws`, `@types/ws`, `@types/node` and `undici-types` with the main package. None of the network-capable modules is reachable from an entry. This is a deliberate 4.x consequence: phase 1 lands on `main`, so 4.1.x patch releases already ship these packages.
- The lockfile is not published, so an adopter's install resolves `@types/ws`'s `@types/node: "*"` to the latest `@types/node` release, not to the 24.19.2 this repository pins for development.
- G9 (Node 24.15 and 26): CI builds, lints, unit-tests and packs on both. Conformance on both versions per pull request is open; the release system test covers it.
- Wire formats, digests and signatures do not change (P7). The CLI surface may change in 5.0 within the invariants of R2. Every changed golden is a ledger row, and the goldens of cases tagged `invariant: true` never change.
- 5.0 breaks the public JS API (R1) and parts of the CLI (R2). `docs/guides/upgrade-5.md` and the CHANGELOG list each change.
- Two styles live side by side until the release; `scripts/effect-inventory.sh` tracks what is left.
- **Risk.** A typed error can turn a refusal into a recoverable branch. Phase 1 adds a lint rule against the combinators that drop a failure (S1.3).
